Start with one box. Raise it.

Tiny Linux microVMs that start in about a second, on a host you own. Create one over SSH; it gets its own HTTPS address behind your team's login.

Install on your host Read the code on GitHub ↗

“Ready” means the VM's SSH server answers, timed by boxe from the moment the command arrives. On our test host that takes 0.7 to 1.0 s; with a cold cache or a busy host, up to 2.5 s.

Ubuntu with sudo, Docker and a disk that stays. Not a container: its own kernel, in its own microVM.

Its own HTTPS address

Port 8000 at quick-fox.boxe.example.com, any port from 3000 to 9999 at quick-fox--3000…. Your team logs in first.

--agentfix thelogin bug

A coding agent in every VM

Shelley, with your own model keys. Set them up once in one VM, then copy it with a task: the copy starts working on it.

sleeping

Sleep, if you turn it on

An unused VM saves its memory to disk and frees its RAM. The next SSH or web request wakes it where it was, in about half a second.

DISPLAY=:1

A desktop with Chrome

In your browser, for the owner only. Agents can use it while you watch.

--ttl 2h

Gone when you are done

Give a VM a time to live and it deletes itself.

Everything is ssh

Nothing to install on your computer: the SSH keys you already have on GitHub let you in, and every answer is plain text.

Then Cloud Hypervisor boots it.

Then it answers on SSH and HTTPS.

SSH goes through boxed as a jump host. HTTPS comes from your TLS proxy to boxed, which logs people in with OIDC.

The VM commands

Run them as ssh boxe <command>, or type ssh boxe alone for a prompt where tab completes commands and your VM names. VM commands support --json, for output a program can read. Put --agent and a prompt last on cp, fork or new to hand the new VM a task; the agent needs models, so copy a VM where you set them up in Shelley.

Once per computer, so ssh <vm>.boxe works and you trust every VM with one CA entry:

ssh boxe ssh-config >> ~/.ssh/config
ssh boxe known-hosts >> ~/.ssh/known_hosts
Commands of ssh boxe
new [name]Create a VM. Options: --cpu 2 --mem 2G --ttl 2h --image <name>
cp <name> [new-name]Copy a VM, even a running one
fork <name> [new-name]Copy a running VM with its memory
imagesThe images new VMs can start from
ls [-a]Your VMs and what they use (-a: everyone's)
restart <name>Power a VM off and on again
ttl <name> <2h|3d|off>Delete a VM by itself after a while
rm <name>Delete a VM
sleep <name>Put a VM to sleep now (if the host has sleep on)
wake <name>Wake a VM up (connecting does too)

share <name> [port]A link to the VM for anyone (port 8000)
unshare <name>Make the VM's links stop working

Runs on one Linux host

One machine with KVM and ZFS runs the whole thing. Bare metal is simplest and fastest: a dedicated server, for example at Hetzner, or a spare PC at home or in the office with hardware virtualization, an SSD and 16 GB of RAM. It needs no public IP: SSH goes through Tailscale, the web through a Cloudflare Tunnel. We test on Ubuntu 26.04 inside a Proxmox VM with nested virtualization, also behind a tunnel. Cloud VMs work only where nested virtualization is offered: GCP, Azure, AWS C8i, M8i and R8i.

  • /dev/kvm and a ZFS pool
  • Cloud Hypervisor v54 or later
  • A guest kernel from cloud-hypervisor/linux
  • Docker, to build the image
  • nftables and iptables
  • For the web: an OIDC provider, and a wildcard DNS record with a TLS proxy such as Caddy, or a Cloudflare Tunnel if the host has no public IP
  • Optional: Tailscale for ssh boxe on your tailnet, restic for nightly backups

  1. Make the pool

    Replace /dev/... with your disk, and keep boxe/sleep for sleep and fork.

    zpool create boxe /dev/...
zfs create boxe/vms
zfs create boxe/images
zfs create boxe/sleep

  2. Build the base image

    exe.dev's exeuntu with a thin layer of ours. Tag it with today's date, here 20261030.

    docker build -t boxeuntu:20261030 image/
sudo scripts/build-base.sh boxeuntu:20261030 boxeuntu-20261030

  3. Set up the host

    An unprivileged boxe-vm user, the network script, the team's GitHub usernames in /etc/boxe/users, the systemd units and /etc/boxe/boxed.env, with -base boxe/images/boxeuntu-20261030@base.

    Sleep and fork are off until you set -sleep-dir /boxe/sleep; add -sleep-after 30m to put unused VMs to sleep.

  4. Deploy

    From your computer, with your host's SSH address in place of me@my-host: it builds boxed, installs it as a new version and rolls back if it does not come up.

    scripts/deploy.sh me@my-host

Made for one team, on one host

VMs are untrusted

Each runs in its own Cloud Hypervisor process, as an unprivileged user with no capabilities, memory and CPU limits, and only its own disks. Each may send only with its own MAC and IP.

Members trust each other on the web

Any logged-in member can open any VM over HTTPS, and apps get the member's email in X-Box-Email, a header they can trust. Share-link visitors are anonymous: no header. Apps still need CSRF protection against other VMs' pages. SSH, the agent and the desktop are for the VM's owner only.

The rest is yours

You secure the identity provider and the TLS proxy or the tunnel. One host, no high availability, not a multi-tenant cloud.
